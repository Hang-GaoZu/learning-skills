# 第 1 步：查看仓库状态

## 目标

学会在修改仓库后先查看状态，避免不了解现场就继续操作。学完能独立判断：当前修改在工作区还是暂存区，以及下一步该运行什么命令。

## 核心概念

`git status` 展示工作区、暂存区和当前分支的状态。它只读取信息，不会提交、删除或修改文件。

在主动学习里，要能回答三个可观察问题：

1. 哪些文件被修改但还没暂存？
2. 哪些修改已经进入暂存区，下一次提交会带上？
3. 当前位于哪个分支？

## 生活类比

沿用“仓库是工作车间”的地图：仓库是车间，工作区是操作台，暂存区是待打包区，分支是当前正在施工的那条生产线。

`git status` 像查看车间告示板：它告诉你操作台上哪些材料被改动、哪些已经搬进待打包区，但不会替你搬材料，也不会把包裹寄出去。

## 主动走查

### 先预测

假设你在测试仓库里只修改了 `notes.txt`，还没运行其他 Git 命令。

先不运行任何命令，回答：

- `git status` 会把 `notes.txt` 放在“已暂存”还是“未暂存”？
- 运行后，文件内容会变化吗？

写下你的答案，再继续。

### 双轨走查

| 节拍 | 比喻状态 | 代码/流程 | 变量或输出 | 用户任务 |
|---|---|---|---|---|
| 1 | 操作台上的 `notes.txt` 被改过，待打包区空 | 执行 `git status` | 输出列出 `modified: notes.txt`，位于 “Changes not staged for commit” | 指出它属于工作区还是暂存区 |
| 2 | 材料从操作台搬进待打包区 | 执行 `git add notes.txt` | 同一文件移到 “Changes to be committed” | 预测再运行一次 `git status` 会显示什么 |
| 3 | 告示板只记录状态，不搬材料 | 再执行 `git status` | 文件仍在待打包区，内容未变 | 说明为什么查看命令没有提交任何东西 |

### 即时反馈

- 若你把第 1 拍判成“已暂存”：错在把“文件被修改”当成了“修改已进入待打包区”。归入“概念混淆”，回到地图确认操作台与待打包区是两个位置。
- 若你答“文件内容会变化”：错在把读取状态的命令当成了写操作。归入“概念混淆”，用 `git status` 的只读性质纠正。
- 若你能说出“工作区改动 ≠ 暂存区改动”，说明这条边界已经建立。

## 变式迁移

改变条件：如果 `notes.txt` 在 `git add` 之后又被修改了一次，`git status` 会怎样显示？

先预测，再看判定要点：

- 同一文件可能同时出现在“已暂存”和“未暂存”两处；
- 已暂存的是上次 `add` 时的版本，未暂存的是之后的修改；
- 这正说明“暂存”保存的是快照位置，不是文件当前的最终内容。

如果这条预测错了，把它归入“边界条件”，在复习队列里记“暂存区保存的是加入时的版本”。

## 代码解释

```bash
git status
```

- `git`：调用 Git 命令行工具；
- `status`：请求显示当前仓库状态；
- 命令不带修改参数，因此只读。

输出要重点看三块：当前分支、已暂存改动、未暂存改动。只读最后一行会漏掉文件所在区域。

## 常见错误

- 在不是 Git 仓库的目录运行后，误把报错当作文件丢失；
- 只看输出最后一行，不看文件处于工作区还是暂存区；
- 把状态查看命令当成提交命令；
- 看到文件出现在输出里，就以为已经被提交。

## 小练习与出口验收

小练习：在一个测试仓库中修改一个文件，运行 `git status`，指出它位于工作区还是暂存区，并说明依据。

出口验收由导师在用户作答后评阅：至少一道应用题；第 1 步没有旧步复习，从第 2 步开始必须加入旧步题。应用题优先采用上面的变式：`add` 之后再次修改同一文件，预测并解释两处输出。

## 总结

先看告示板，再决定材料的下一步去向；工作区是操作台，暂存区是待打包区，查看不等于交付。
