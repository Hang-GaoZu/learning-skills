### 构建命令逐词拆解

`gcc hello.c -o hello.exe`：

- `gcc`：编译器，把人写的 C 源码翻译成机器能跑的程序；
- `hello.c`：输入，也就是你的源码文件；
- `-o`：output 的缩写，指定生成的程序叫什么名；
- `hello.exe`：输出产物，Windows 下能直接运行的可执行文件。

### Git 首提交

```
git add .
git commit -m "第0步 环境自检通过"
```

- `git add .`：把当前目录所有改动封进暂存区（`.gitignore` 里列的 exe 不会被收）；
- `git commit`：存档，`-m` 后面是这一存档的标签。

## 先预测

在 `hello.c` 里写下只打印一行字的代码，然后编译运行。**先不运行**，回答：

1. 编译成功时，终端会不会有额外输出？
2. 如果代码里漏了分号，是编译时报错，还是运行时报错？

写完你的答案，再往下看。

---

### 判定要点（作答后再看）

- 答"编译时有输出"：对了一半——`gcc` 默认静默，**成功即无输出**，但那不是报错。
- 答"运行时报错"：错在把语法检查和运行时混作一处。漏分号属于**语法错误**，编译阶段就拦下，程序根本不会生成。
- 归入"概念混淆"：编译期与运行期是两道关。

## 双轨走查

| 节拍 | 状态变化 | 代码/流程动作 | 终端输出 | 用户任务 |
|---|---|---|---|---|
| 1 | 无程序文件 | 写 `hello.c` | — | 说出这时代码还没变成程序 |
| 2 | 生成 `hello.exe` | 执行 `gcc hello.c -o hello.exe` | 无输出（成功即静默） | 判断"没输出"是好是坏 |
| 3 | 程序被运行 | 执行 `.\hello.exe` | 一行 `hello snake` | 指出这行字从哪来 |
| 4 | 语法错误，无程序 | 删掉一个分号再编译 | 报 `expected ';'` 之类 | 说出错误发生在哪一道关 |

## 运行与观察

- 启动命令：`gcc hello.c -o hello.exe; .\hello.exe`
- 预期输出：`hello snake`
- 若不一样，先看这三处：
  1. 当前目录是否就是 `hello.c` 所在目录；
  2. 路径里有没有中文或空格（有就换到纯英文路径重试）；
  3. `gcc` 是否真的在 PATH 里（`gcc --version` 能不能出声）。

## 定位修正

| 现象 | 层 | 最小提示 |
|---|---|---|
| `gcc 不是内部或外部命令` | 环境 | "`gcc --version` 能出声吗？如果也不能，问题不在代码，在工具装没装或 PATH。" |
| 编译成功但运行不出字 | 逻辑（输出） | "`printf` 后面那对括号里，你真的写了要打印的东西吗？" |
| 输出乱码 | 环境（编码） | "终端编码和源码编码是不是同一套？先试试只打英文。" |

## 变式迁移

把 `printf` 里的 `hello snake` 改成中文"你好，蛇"。预测：终端会正常显示，还是变成乱码方块？为什么？

答对要点：取决于终端编码（代码页）与源码编码是否一致；UTF-8 源码配 GBK 终端就会乱码。这也正是第 2 步之后要坚持用 ASCII 画棋盘的原因。

## 常见错误

- 在错误的目录下编译，报"找不到文件"；
- 把"编译成功没输出"误当成失败；
- 中文路径导致编译失败，却以为是语法写错；
- 直接双击 `.exe`，看不到报错信息，问题无从定位。
