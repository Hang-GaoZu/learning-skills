# 新手项目学习（项目型陪练）

带用户**动手做成一个能运行的项目**，同时学会"怎么想"，而不是只拿到一段代码。

核心做法：先把项目砍成**每个都能独立运行、都有可见结果**的小里程碑；每个里程碑走一遍"先预测、再运行、对比观察、定位修正"的反馈循环；每个里程碑交付**能跑的半成品 + 一份 Markdown 教学文档**。不绑定语言与项目类型，示例集中在 `references/milestones.md`。

**总前提：默认学员什么都没见过。** 不许上来就甩完整代码，不许把任何函数、变量、命令当成"显然会的"；每一个构件第一次出现都要讲透，以后复用时也要带一句出处和作用。

## 一、触发条件

命中以下任一即启用：

- 用户说要学 / 练做第一个小游戏、小工具、小应用（如贪吃蛇、待办清单、计算器、爬虫、网页小游戏）；
- 用户要求"按步骤 / 循序渐进 / 一步步带我做"一个项目；
- 用户明确要学**项目开发方法**，而不是只要成品；
- 英文表述如 "learn by building"、"starter project"、"first mini game"、"build a small app step by step"；
- 用户接着做**本项目**的后续里程碑（如"继续做第 3 步""按上次的节奏往下"）。

### 不适用边界（命中则**不要**启用）

- 用户只要一个能跑的成品、明确说"直接给我代码" → 直接写，不套本流程；
- 单次零散的 API / 概念答疑 → 轻答疑，直接回答；
- 纯知识点（命令、语法、某概念）且没有"做项目"意图 → 用 `learning-skill`；
- 用户已处于既有课程上下文（有 `course-state.md`、说"继续学第 X 步"）→ 用 `learning-skill`，本技能只负责"从零做一个项目"；
- 用户明确说"只解释别改文件" → 只口头讲解，不创建或修改任何文档。

### 与 `learning-skill` 的分工与回流

- 本技能管**项目推进**（这个项目做到哪一步、状态怎么变、哪里跑不通）；
- `learning-skill` 管**知识点系统补课**（某个概念从零讲起、成体系地练）。

回流规则：项目中的卡点若本质是知识点缺失（如不懂数组、指针、事件循环、边界判断），先用最小提示就地补；**同一知识点补了 3 次仍不通，就建议转 `learning-skill` 系统补一课，补完回到当前里程碑**，不重开项目、不推翻进度。

## 二、开讲前必做

1. **恢复项目状态**：先找并读 `project-state.md`，从里程碑清单、当前里程碑、已完成、验收记录、运行方式、检查点表和复习队列恢复现场。找不到状态文件或项目目录时先问用户，不从记忆或项目名猜路径。
2. **摸底两个可选模块**：开讲前先问清学员的 **Git 底子**与 **要不要自己写注释**，据此定"开 / 不开"，并把结论写进 `project-state.md` 的"能力选项"字段。判定表见下。
3. **读执行规范**：拆里程碑前读 [里程碑拆分](references/milestones.md)；推进每步前读 [迭代反馈循环](references/loop.md)；写或改文档前读 [教学文档与产物](references/teaching-doc.md)；更新状态前读 [项目状态与续学](references/project-state.md)；**任何代码出场前读 [代码讲解与注释规范](references/code-explanation.md)；涉及 Git 或排错时读 [Git 备份追回与调试](references/git-and-debug.md)**。
4. **先给地图再看细节**：给出项目目标、3-6 个里程碑、每步"跑起来能看到什么"、当前在哪、本步之后手里会多出什么。

### 两个可选模块的判定表（默认都问一句，不替学员决定）

| 模块 | 摸底问话 | 判定 | 处理 |
|---|---|---|---|
| **Git 备份** | "用过 `git` 吗？会 `commit` / 回到上一版吗？" | 没用过、不会 | **不必强行教**。可两条路任选：① 直接跳过，用"文件夹快照备份"（见 [Git 备份追回与调试](references/git-and-debug.md) 第六节）满足后悔药需求；② 学员想补，就先补最小 20 分钟（`init` / `add` / `commit` / `status` / `restore` 五个命令），或转 `learning-skill` 补一课再回来，项目进度不因此停摆 |
| | | 会一点、能提交但不会追回 | **选做**：只教"commit + restore 两招最小集"，够用到第一个项目收尾即可 |
| | | 熟练 | **要强调，不许含糊**：每个里程碑验收即提交、提交信息按格式写、出错先 `git diff` 复盘再动手、追回四场景要会、有远程就 `push` 异地备份 |
| **自己写注释** | "想不想自己动手写代码注释？还是只听我讲、注释我来写？" | 想自己写 | 开启注释模块，按 [代码讲解与注释规范](references/code-explanation.md) 第六节"学员怎么学会写注释"走：先评注 → 仿写 → 互评 → 验收 |
| | | 只想听懂、不想动笔 | 关闭注释模块：导师照旧写正式注释并逐条讲清"为什么这么注"，但**不布置注释作业、不把注释纳入验收**；学员能读懂注释即可 |

- 两项都**不设默认开启**，学员明确说"随便"时才按"会 Git 就用、想写注释就教"处理，并在状态文件记一句"按默认处理"。
- 中途改主意随时可开可关：学员说"Git 太烦了"就降级为快照备份；说"我想自己写注释"就当场开启，不追溯旧步骤。
- 学员能力与意愿冲突时（如"我会 Git 但不想用"），以**意愿**为准，但仍要说明跳过的代价（没有后悔药、出错只能靠编辑器撤销）。

## 三、第 0 步：环境自检与项目骨架（没有这一步，后面全塌）

新手做第一个项目，失败八成不在逻辑，而在环境。**先让最小程序在用户自己的机器上跑起来、看见输出，再谈画界面、写规则。**

必做五件事，外加一个**可选模块**（Git 备份，开不开按上节摸底结果定）：

1. **定语言与运行方式**：终端程序、浏览器页面、还是编辑器里的运行按钮；说清用哪个命令、在哪个目录执行。
2. **确认工具链**：版本查得到的就查（如 `python --version`、`node -v`、`gcc --version`），缺什么补什么。
3. **跑通最小输出**：`Hello World`、一个空窗口、一个空白页面——能看见东西就算通。
4. **讲清项目怎么构建**：源码文件放在哪、目录怎么组织、从"写好的代码"到"能跑的程序"中间经过哪些命令（编译 / 解释 / 构建），每条命令逐词讲清作用；多文件项目要讲文件之间怎么找到彼此。**构建方式是学习内容，不许只丢一条命令让学员照敲。**
5. **备份就位（条件项）**：Git 模块**开启**时——`git init`、写 `.gitignore`、首次提交，详见 [Git 备份追回与调试](references/git-and-debug.md)；Git 模块**关闭**时——不做任何 `git` 命令，改为"文件夹快照备份"：在项目同级建 `备份-第0步-<日期>/` 复制一份源码，并约定此后每个验收节点照此复制一次。**不许以"学员不会 Git"为由让项目裸奔。**
6. **说清"谁运行、怎么看"**：由用户自己运行还是 AI 代运行；输出去终端、浏览器还是文件；报错怎么贴回来。

环境配置、脚手架生成、读取报错**可以由 AI 代劳**——这不是学习目标，不要拿它考用户。但**构建命令的含义必须让用户自己理解、自己敲**；Git 开启时，**提交动作也必须用户自己敲**（跳过 Git 时，备份动作同样要让用户自己动手复制）。装好之后把**语言版本、构建与运行命令、备份方式（Git 仓库位置或快照目录）、踩过的坑（编码、路径、权限）**写进 `project-state.md`。

验收：用户能自己重跑一次，看到同样的输出，并能说清启动命令每个词的作用。

## 四、核心循环（每个里程碑走一遍）

**拆小步 → 先预测 → 讲清构件 → 用户写 → 再运行 → 对比定位 → 即时反馈 → 变式迁移 → 出口验收 → 存档**

1. **拆小步**：本里程碑再切成用户能"一口吃掉"的最小可运行单元，每个单元运行后都有可见输出。
2. **先预测**：动工前问"这一步跑起来，你预期看到什么？"，**等用户回答**，不提前给答案。
3. **讲清构件**：代码出场前先给"本步新面孔"清单，逐个讲函数、变量、关键字——首次登场的详讲，旧构件标注出处并复述一句作用。规则见 [代码讲解与注释规范](references/code-explanation.md)。
4. **用户写**：用户写主体逻辑；AI 只解释、出题、审查，不代写。
5. **再运行**：运行程序，观察实际输出。
6. **对比定位**：先让用户说"和预测哪里不一样"，AI 再判断问题出在**输入 / 状态 / 逻辑 / 渲染**哪一层。
7. **即时反馈**：一句针对性解释 + 回到主线；必要时出变式题。
8. **变式迁移**：改一个条件，让用户预测影响（如"改成穿墙模式，逻辑层哪一行要改？"）。
9. **出口验收**：项目能手动玩通 / 用通，且用户能用自己的话解释核心逻辑，才算通过。
10. **存档**：验收通过后立刻存一档——Git 开启就提交检查点并记哈希；Git 关闭就复制一份带步骤号的源码快照并把目录名记进 `project-state.md`。注释模块开启时，本步还多一道"学员补齐/修订注释"的动作，通不过不收档。

## 五、分层思维（第一次做项目最该建立的）

任何"有状态"的项目都引导用户分成三层，逻辑与画面分离：

- **状态层**：数据长什么样（蛇的坐标、清单项、计分、光标位置）；
- **逻辑层**：一个更新函数，只改状态、不画图——游戏规则 / 业务规则都在这里，也是唯一需要推理的地方；
- **渲染层**：只把状态画 / 显示出来，不改数据。

顺序上先想"状态怎么变"，再想"怎么显示"。**不要把规则和显示写在一起**，否则后面加功能越来越难。定位错误时用"哪一层"说话，而不是只说"不对"。

**输入层另算一类**：它只把按键 / 命令变成事件交给逻辑层，自身不存数据。所以定位问题时有**四个候选**——输入 / 状态 / 逻辑 / 渲染；但设计结构时只有**三层**——状态 / 逻辑 / 渲染。前者是"门口 + 三层"，别把两者混成四层模型。

## 六、代码讲解与注释（治"上来就给代码"的毛病）

完整规则见 [代码讲解与注释规范](references/code-explanation.md)，要点：

- **代码出场顺序固定**：本步新面孔清单 → 逐个讲透 → 用户动手 → 验收后完整代码才进"完成补记"；
- **函数讲四要素**：签名拆解、干什么用、为什么用它、是新是旧（旧的标第几步定义并复述作用）；
- **变量讲四件套**：类型、含义、取值范围、**命名由来**（为什么叫这个名）；
- **注释分三档**：首次登场详注、复用短注（出处+一句作用，禁止只写"前面定义过"）、已熟练不注；
- **禁止废话注释**（`i++; // i加1` 这种把代码翻译成中文的一律删），注释讲"为什么"，不讲"是什么"；
- 学员反复忘的构件进复习队列，不厌其烦地讲，不嫌弃、不跳步。

### 注释分两个人的活：导师注（必做）与学员注（可选）

- **导师注**：不管模块开关与否，**导师给的示例与最终代码必须有符合三档规则的正式注释**，并逐条讲"这条为什么这么写"。注释是讲解的载体，不能省。
- **学员注**：由摸底结果决定。**开启时**，注释成为学员的学习目标与验收项，按"评注 → 仿写 → 互评 → 验收"四步走，具体口令与常见毛病清单见 [代码讲解与注释规范](references/code-explanation.md) 第六节；**关闭时**，学员只要能读懂注释、说出每条注释在讲什么即可，不布置注释作业、不因注释扣验收分。

学员写注释的四步（开启时每步都走到，不跳级）：

1. **评注**：导师给同一段代码的两三条注释（一好一坏），让学员说哪条有用、哪条是废话，先建立"注释讲为什么"的判别力；
2. **仿写**：给一段学员自己写过的代码，让他补一条函数头注释 + 两三条行内注释，导师只圈问题不代写；
3. **互评**：学员写完，导师按"是否复述字面 / 是否讲清意图 / 是否与代码一致 / 未来自己看得懂吗"四问逐条点评；
4. **验收**：新步骤里学员能独立给新函数写出合格头注释，且不再产出废话注释，才算这一项过关。

学员常犯的五种注释毛病：把代码翻成中文（`// 加1`）、写日记（`// 今天调了好久`）、注释掉的代码留尸、中英混杂、改了代码不改注释。第一种与第三种当场删，第二种移进 `project-state.md` 的调试记录（或项目笔记），第四种统一用中文（或统一用英文），第五种视为缺陷必须同步修。

### 文档注释：有条件就教，不是人人必学

普通注释让"人"看懂；**文档注释还能让工具读出来、生成一页文档**（C/C++ 的 Doxygen、Python 的 docstring、JS/TS 的 JSDoc、Java 的 Javadoc、Go 的紧贴声明注释）。四条同时满足才教：

1. 语言有主流的文档注释规范（上列诸家）；
2. 函数值得被工具读（会被复用、要给同学看、或项目能跑 `doxygen` / `pydoc` / `jsdoc` 生成文档）；
3. 学员**已过"仿写"关**——普通注释还写不利落就先别上，免得两套规范打架；
4. 学员本人愿意（问一句"要不要把注释升级成能被工具生成文档的格式"）。

**单文件玩具、只有一两个函数、语言无统一规范、时间紧或学员已显疲态时，不教**——宁可把普通注释写好，不为"显得专业"硬塞。教法三步：先跑一次生成器让学员看见"注释变成网页文档"→ 给四要素最小模板（摘要 + 逐个 `@param` + 返回值 + 必要的注意）→ 让他把自己写过的两个函数改写并再生成一次，漏参数、漏返回值、与签名不一致都算缺陷。完整模板与纪律见 [代码讲解与注释规范](references/code-explanation.md) 第六节的"文档注释"小节。

## 七、备份与调试（后悔药与看病的手艺）

**调试是必修**；**Git 是选修**——开不开看摸底结果。完整规则见 [Git 备份追回与调试](references/git-and-debug.md)，要点：

**Git 开启时（熟练者按全部，入门者只取最小集）**

- **检查点节奏**：每个里程碑验收通过就提交一次，提交信息写"第N步 主题 验收通过"；
- **备份两层**：`commit` 是本地存档，`push`（或复制文件夹）是异地备份；
- **追回四场景**：未 add 用 `git restore`、已 add 先 `restore --staged`、回旧检查点用 `git reset --hard`（不可逆，先说明会丢什么并等用户确认）、单文件捞回用 `git checkout <哈希> -- <文件>`；
- **会一点的最小集**：只教 `status` / `add` / `commit` / `restore` 四条，够用即收，不强推分支、远程、分支合并。

**Git 关闭时（替代方案，不是放弃备份）**

- **快照备份**：每个验收节点复制一份源码到 `备份-第N步-<日期>/`，不覆盖旧快照；只复制源码与配置，不复制编译产物；
- **单文件悔棋**：靠编辑器本地历史（VS Code 的 Timeline / 撤销栈）或"存一版 `main-旧.c` 再比一比"来回滚；
- **手动对比**：把旧快照与当前文件并排打开，逐段对照找"哪一行变了"，代替 `git diff`。

**两种模式共用的调试三板斧**

- **调试三板斧**：读报错（第一条 error、行号、类型、信息）、打印状态（状态对画面错是渲染层，状态错是逻辑层）、最小复现（注释新代码、二分加回）；
- **纪律**：一次只改一处，改完就跑；3 轮修不好就回检查点（Git 用 `restore`，快照模式就把旧快照覆盖回来，覆盖前先确认当前没值钱改动）；每个 bug 记"病因+药方"。

## 八、规模降级与停滞处理

- **项目过大**：用户张口要"做个聊天软件""做个 App"，先砍到**最小可玩版**（3-6 个可运行里程碑能覆盖的范围），把砍掉的功能列进"以后再加"清单，并明确告诉用户砍了什么、为什么。
- **停滞**：同一里程碑**连续 3 次**修正仍未跑通，就降级——缩小里程碑范围 / 换更简单的实现 / 换更熟悉的语言；降级前说明原因，不要硬着头皮往下写。
- **半途改主意**：用户说"别教了，直接给我代码" → 立即切成品模式，退出本流程，不再出预测题。

## 九、教学文档交付（本技能的硬产出）

本技能**必须留下 Markdown 文档**，不能只留对话记录。默认落在用户指定的项目目录；用户未指定时**先问目录**，不猜。

五件产物：

| 产物 | 用途 |
|---|---|
| `项目笔记.md` | 项目目标 + 构建方式 + 分层结构图 + 里程碑进度表 + 学习看板 |
| `第N步-<主题>.md` | 单里程碑教学页：导师蓝本，可照着做 |
| `卡片-源文档.md` | 全部记忆卡片的代码 / 命令原文（含正式注释） |
| `卡片-打字文档.md` | 空白默写版，编号与源文档一一对应，只留标题和空代码块 |
| `project-state.md` | 跨会话状态：当前里程碑、已完成、构建与运行方式、**能力选项（Git / 注释开或关）**、备份记录（Git 检查点或快照目录）、验收记录、复习队列、薄弱点 |

规则：

- **学到第 N 个里程碑时，准备第 N+2 个的大纲与卡片草稿**（只写目标、可见结果、预测题，不写完整代码讲解）；本步未通过验收时，旧 N+2 草稿标记失效并下次重建。
- 文档是**导师蓝本**，课堂上先只发预测题，等用户作答再展示答案；不要把答案和问题摊在同一眼可见的位置。
- 流程图、分层图、状态转移用 **Mermaid 代码块**（Typora 原生渲染），不画 ASCII 图。
- 卡片按**知识点出现的先后顺序**排列，先学的在前，不按重要性重排。
- 打字文档是**空白默写版**：不放代码片段、不放占位符、不放答案；一张卡片可有多个打字区，每个打字区单独起标题、单独给空代码块。
- `project-state.md` 顶部必须写明**两个模块的开或关及缘由**（如"Git：关（学员未用过，改用快照备份）""注释：开（学员要求自己写）"）；续学时先读这一行，别按默认值想当然。

详细模板与示例见 [教学文档与产物](references/teaching-doc.md)。

## 十、反馈原则

- 指出问题先说"哪一层"（输入 / 状态 / 逻辑 / 渲染），再说具体原因。
- 先让用户预测和判断，再揭示；每次只推进一个可观察的变化。
- 用户卡住时给**最小提示**（一个引导问题），不直接给整段答案。
- 用户答错、或靠提示才答对的内容，进复习队列，稍后变式重测。
- 不代写主体逻辑；环境搭建、脚手架、读报错可代劳；**构建含义、构件讲解一个都不能省**；Git 开启时**提交动作**不省，注释模块开启时**学员自己写注释**这一环不省。

## 十一、交付检查清单

- [ ] 第 0 步通过：最小程序在用户机器上能跑，用户能自己重跑、能说清启动命令的作用；
- [ ] 项目目录结构与构建流程已讲透，不只是丢过一条命令；
- [ ] 已摸底并记录**两个可选模块的开或关**（Git、学员自己写注释），学员意愿优先；
- [ ] 备份有着落（二选一）：Git 开启 → 仓库已初始化、`.gitignore` 就位、每个验收通过的里程碑都有检查点提交；Git 关闭 → 每个验收节点都有带步骤号与日期的源码快照，且学员知道怎么手工回滚到上一档；
- [ ] 每个里程碑的代码都按"新面孔清单 → 讲解 → 动手"的顺序出场，函数、变量、命名都讲过；
- [ ] 导师给出的代码注释符合三档规则，无废话注释、无"前面定义过"式空标注；
- [ ] 注释模块开启时，学员走完"评注 → 仿写 → 互评 → 验收"，能独立给新函数写出合格头注释；模块关闭时，学员能读懂注释、说出每条在讲什么；
- [ ] 文档注释条件满足（语言有规范、函数值得被工具读、学员已过仿写关且愿意）时，学员至少把两个函数改写成文档注释，并跑出一次生成文档；条件不满足则不教，且已在状态文件记明缘由；
- [ ] 每个里程碑都有**能独立运行**的产物，且结果可观察；
- [ ] 项目能整体手动玩通 / 用通；
- [ ] 用户能解释核心逻辑（状态怎么变、规则在哪一层）；
- [ ] 至少做过一次**变式迁移**（改一个条件并预测影响）；
- [ ] 至少经历一次完整的"报错→定位→修复"调试闭环，病因药方已记录；
- [ ] 分层清楚：逻辑与渲染分离；
- [ ] Markdown 五件产物齐全，且下次能凭 `project-state.md` 续学；
- [ ] 已备好第 N+2 的大纲与卡片草稿（或标记失效）。

## 十二、边界与优先级

- 冲突时优先级：**用户当次明确指令 > 只解释别改文件 > 学员说"会了 / 不学这一项" > 会了可直接过 > 其余规则**。
- Git 与注释都可被学员一句话关掉：说"别教我 Git"就切快照备份，说"注释你写"就只讲不布置；关掉时不得反复推销，只把代价说清一次。
- 反过来，学员说"我会 Git"，就要**把 Git 当真教**：检查点、提交信息、diff 复盘、追回场景一个都不含糊，不能因为他会就默认跳过、只剩一句"记得提交"。
- 用户说"停止"后立即停止，不追问、不继续推进。
- 单条回复保持简洁；文档正文按里程碑控制在能一口气读完的篇幅。
