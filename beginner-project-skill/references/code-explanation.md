# 代码讲解与注释规范

新手怕的从来不是代码多，而是"黑话多"：一个函数名砸过来，不知道它是新是旧、干什么用；一个变量名不知道为什么这么叫。导师觉得"这不是显然吗"，学员却两眼一抹黑。**默认学员什么都没见过，是本文件的总前提。**

## 一、代码出场的固定顺序（不许上来就甩完整代码）

每一小段代码，都按这个顺序出场：

1. **先给"本步新面孔"清单**：本步涉及的函数、变量、关键字，哪些是首次登场、哪些是老熟人，一张表说清；
2. **逐个讲透**：按下面的函数 / 变量讲解规则，一个一个讲；
3. **再让用户动手写**（骨架或主体）；
4. **完整代码只在用户写过、跑通、验收后**，作为对照进入教学页"完成补记"和卡片源文档。

顺序错了就是"填鸭"——学员照着抄完，知其然不知其所以然。

## 二、"本步新面孔"清单（单步教学页强制区块）

放在代码块之前，模板：

| 名称 | 种类 | 新/旧 | 一句话作用 |
|---|---|---|---|
| `snake_x` | 变量 | 首次登场 | 蛇头的横向坐标 |
| `printf` | 库函数 | 首次登场 | 把内容按格式打印到终端 |
| `draw_board` | 自定义函数 | 旧（第 1 步定义） | 画棋盘，本步原样复用 |
| `for` | 关键字 | 旧（第 1 步定义） | 按次数重复执行 |

- "旧"的必须写清**第几步定义、当时干什么、本步拿它做什么**，不许只写"前面讲过"。
- 学员对旧构件的记忆是"狗熊掰棒子"——掰一棒丢一棒，清单就是帮他把棒子捡回来。

## 三、函数讲解四要素（首次登场，一个都不能少）

1. **签名拆解**：返回值、函数名、参数分别是什么意思。例：`int rand(void)` —— `int` 表示它会还给你一个整数，`void` 表示它不要参数。
2. **干什么用**：喂给它什么、它吐出什么、在本项目里承担哪一层的活。
3. **为什么用它 / 为什么这样设计**：为什么要单独封一个函数，而不是把代码糊在一起；为什么选它不选别的写法。
4. **出处与去向**：首次登场标"新面孔"；以后再出现一律标"← 第 N 步《主题》定义，当时用来……，本步用它……"。

自定义函数还要讲：**函数名是怎么起的**（动词开头、见名知意，如 `check_collision` = 检查碰撞）。

## 四、变量讲解四件套

每个首次登场的变量，讲清：

1. **类型**：int 是整数、char 是一个字符……类型决定它能装什么；
2. **含义**：它在项目里代表现实中的什么东西（蛇头坐标、分数、方向）；
3. **取值范围**：最小多少、最大多少、谁会改它（与状态设计表呼应）；
4. **命名由来**：为什么叫这个名。例：`snake_x` —— `snake` 表明主人是蛇，`x` 是数学里横向坐标的惯例名，合起来就是"蛇的横向位置"。

### 命名惯例小词典（第一次用到时讲，之后复用标注即可）

| 名字 | 惯例含义 |
|---|---|
| `i`、`j`、`k` | 循环计数器，按嵌套层次依次用 |
| `x`、`y` | 横向 / 纵向坐标 |
| `n` | 数量、个数 |
| `len` / `length` | 长度 |
| `tmp` | 临时变量，用完即弃 |
| `ret` / `result` | 准备返回的结果 |
| `score` | 分数 |
| `flag` | 标志位，通常只有 0/1 两种状态 |

- 命名风格随语言走：C 常用下划线 `snake_x`，网页 / JS 常见小驼峰 `snakeX`；第一次出现时说明。
- 学员起了坏名字（`a1`、`bbb`）要当场纠正，并说明"名字是给未来的自己看的"。

## 五、注释密度三档（不盲目注，也不漏注）

**注释是"导师注（必做）+ 学员注（可选）"两层。** 导师给出的代码无论模块开关都按本档规则注释；学员自己动笔写注释属可选模块，开不开在开讲前摸底时定（见 `SKILL.md` 的"两个可选模块判定表"，以及本文件第六节）。

| 档位 | 对象 | 注释写法 |
|---|---|---|
| 详注 | 首次登场的函数、变量、关键字 | 作用 + 为什么这样用，可占一整行 |
| 短注 | 复用的旧构件 | 标注出处 + 一句作用，如 `draw_board();  // 第1步的画棋盘函数，先把旧棋盘清出来` |
| 不注 | 学员已连续 3 次正确使用、且能自己复述作用的构件 | 保持干净 |

### 注释写在哪

- **函数头注释**：一句话作用 + 参数和返回值含义，每个自定义函数都要有；
- **行内注释**：只在"为什么这么写"不显然时写，解释意图，不复述字面；
- **分区注释**：`/* ===== 输入处理 ===== */` 这种，标出代码块的分界。

### 三条禁令

1. **禁止废话注释**：`i++;  // i 加 1` 这种把代码翻译成中文的，一律删——注释要讲"为什么"，不讲"是什么"；
2. **禁止只写"前面定义过"**：旧构件复用时必须带一句作用，学员的遗忘是常态，不是态度问题；
3. **禁止注释与代码不一致**：改了代码就必须改注释，过期注释比没有注释更害人；注释掉的废弃代码不留，git 才是后悔药。

## 六、教学员自己写注释（可选模块）

**先定开关**：开讲前问一句"想不想自己动手写注释？还是只听我讲、注释我来写？"——愿意写才开这一节；不愿意就关闭模块，导师注释照写、逐条讲清"为什么这么注"，学员**能读懂、能说出每条注释在讲什么**即可，不布置注释作业、不把注释计入验收。**不许不问就默认教学员写，也不许学员想学却以"注释不重要"打发。**

### 为什么值得单独教

注释是"写给未来自己的信"：三天后回看代码的人，正是学员自己。教学员写注释，实质是教他**把意图讲清楚**——能写出一条合格的"为什么"，说明他真懂了这段逻辑；只会写"i 加 1"，说明他只看到字面。所以这一节既是写作训练，也是理解验收。

### 四步法（一步都不许跳）

**第一步：评注（先建立判别力，不动笔）**

给同一段代码配两三条注释，让学员挑"哪条有用、哪条是废话、为什么"。示例：

````c
// 反例 A：把代码翻成中文，等于没说
score = score + 10;   // score 加 10

// 反例 B：写心情日记，与代码无关
score = score + 10;   // 今天调这个调了好久，终于对了

// 正例 C：讲清"为什么是 10"
score = score + 10;   // 吃到一个食物记 10 分，与界面上显示的每格分值一致
````

提问口令：**"这三条里，哪一条不是给未来的自己看的？"** 等学员答完再点评，别自问自答。

**第二步：仿写（给代码，不给答案）**

挑一段**学员自己写过的**代码（自己写的才有话可说），只提要求，不给范本：

> 请给 `draw_board` 补一条函数头注释（一句话作用 + 参数和返回值含义），再挑两处"不写就容易被未来的自己误解"的地方，各加一条行内注释。

导师只做三件事：圈出问题、指认它属于哪种毛病、提出一个引导问题（如"这句注释讲的是它做了什么，还是你为什么这么做？"），**不代写、不改成自己的句子**。

**第三步：互评（四问过筛）**

学员交稿后，按四问逐条点评，每条给"过 / 不过 + 一句理由"：

| 四问 | 不过的典型表现 |
|---|---|
| 讲的是"为什么"还是"是什么"？ | `i++; // 自增` |
| 未来三天后的自己看得懂吗？ | 满篇术语缩写、指代不明（"这里用那个"） |
| 与代码当前行为一致吗？ | 代码已改成 20 格，注释还写 10 格 |
| 该注的地方漏了吗？ | 自定义函数没有头注释、魔数没解释 |

**第四步：验收（能独立产出才算过）**

新步骤里，学员能**未经提示**给新函数写出合格头注释、且不再产出废话注释，这一项才算 ✅。连续两个步骤都达标，可降为"只抽查"。

### 文档注释：有条件就上一层楼（可选中的可选）

普通注释让"人"看懂，文档注释还能让"工具"读出来、生成一页文档。它值得教，但**有前提**——先判四条，同时满足才教：

| 条件 | 说明 |
|---|---|
| 语言有主流文档注释规范 | C/C++ 用 Doxygen `/** … */`；Python 用 docstring `"""…"""`；JS/TS 用 JSDoc；Java 用 Javadoc；Go 用紧贴声明的 `// 函数名 …` |
| 函数值得被工具读 | 函数会被复用、要给同学看、以后自己还要查，或项目能跑 `doxygen` / `pydoc` / `sphinx` / `jsdoc` 生成文档 |
| 学员已过"仿写"关 | 普通注释还写不利落就先别上文档注释，免得两套规范互相打架 |
| 学员本人愿意 | 问一句"要不要把注释升级成能被工具抓出来、生成文档的格式"，愿意才教 |

**不教的情形（宁可把普通注释写好）**：单文件玩具、只有一两个函数、语言没有统一规范、时间紧、学员已显疲态。**不要为了"显得专业"硬塞**——"强弩之末，势不能穿鲁缟"，学不进去的规范等于没教。

**教法三步（每步都有可见结果）**

1. **先看效果**：导师先写两条文档注释，跑一次生成器（C：`doxygen -g` 后 `doxygen`；Python：`python -m pydoc -w 模块名`；JS：`npx jsdoc`），让学员亲眼看到"注释变成了网页文档"。眼见为实，比讲十句规范有用。
2. **给最小模板**：只教四要素——一句话摘要、`@param` 逐个参数、`@return` / `@returns` 返回值、必要时一句"注意 / 前提"。字段名照语言规范写，不自己发明。
3. **学员改自己的**：挑他自己写过的两个函数，把头注释改写为文档注释，再生成一次文档，对照"哪里漏了参数说明"。缺参数、缺返回值、与签名不一致，都算缺陷，必须补齐。

**各语言最小模板**（参数名必须与真实签名逐字一致，写错名字生成器会静默漏掉）

````c
/**
 * @brief 判断坐标是否落在棋盘边界上
 * @param x 列号，从 0 开始
 * @param y 行号，从 0 开始
 * @return 1 表示在边界，0 表示不在
 */
int is_border(int x, int y);
````

```python
def is_border(x: int, y: int) -> int:
    """判断坐标是否落在棋盘边界上。

    Args:
        x: 列号，从 0 开始。
        y: 行号，从 0 开始。

    Returns:
        1 表示在边界，0 表示不在。
    """
```

```javascript
/**
 * 判断坐标是否落在棋盘边界上
 * @param {number} x 列号，从 0 开始
 * @param {number} y 行号，从 0 开始
 * @returns {number} 1 表示在边界，0 表示不在
 */
function isBorder(x, y) {}
```

**三条纪律**

- 文档注释与普通头注释**不要两套并存**：自定义函数统一用文档注释，普通行内注释只在讲"为什么这么写"时出现；
- 字段照规范写，`@param` 后的参数名与签名逐字一致；
- 生成器跑得通就跑一次给学员看效果；跑不通（缺依赖、网络不通）就只当格式规范用，不在这上面耗时间——环境属于"可代劳"的范畴。



1. **自定义函数必须有头注释**：一句话作用 + 参数含义 + 返回值含义；
2. **行内注释只写"为什么"**：为什么取这个值、为什么先判这个条件、为什么这里要兜底；
3. **复用旧构件写短注**：`draw_board();  // 第1步的画棋盘，本步先清旧画面`——出处加一句作用，不写"前面定义过"。

### 五种常见毛病与处置（当场处理，不积压）

| 毛病 | 例子 | 处置 |
|---|---|---|
| 把代码翻成中文 | `x++; // x 加 1` | 当场删，并追问"这条注释能告诉你任何代码里看不出的信息吗" |
| 写日记 / 情绪 | `// 调了一小时终于通了` | 迁到 `project-state.md` 的调试记录（或项目笔记），代码里不留 |
| 注释掉的代码留尸 | `// draw_board();` | 直接删；要留版本就靠 Git 检查点或源码快照，不靠注释 |
| 中英混杂、术语乱缩 | `// 这里 set 一下 buf` | 全文统一一种语言、术语首次出现给全称 |
| 改了代码不改注释 | 注释写 16 格、代码是 20 格 | 视为**缺陷**，与代码错误同级，必须同步修 |

### 收尾口径

- 注释模块开启：学员注释稿与导师定稿的差异**要点评到位**，学员的合格注释保留进卡片源文档（那是他自己的话，比导师的句子更能唤起记忆）；
- 注释模块关闭：不做评注/仿写练习，但导师注释仍进卡片源文档，学员只需能复述每条注释的含义；
- 无论开关，**打字文档都不夹带注释**（默写练的是代码本体）。

## 七、代码块内的示范格式

````c
/* 画棋盘：把 20×20 的格子打印到终端（第 1 步定义，本步原样复用） */
void draw_board(void) {
    for (int y = 0; y < SIZE; y++) {        // y：行号，外层循环管行（第1步惯例）
        for (int x = 0; x < SIZE; x++) {    // x：列号，内层循环管列
            putchar(is_border(x, y) ? '#' : ' ');  // is_border 是本步新函数，判断是否在边界
        }
        putchar('\n');
    }
}
````

- 首次登场的构件，注释可以密；同一段代码在后面步骤复用时，注释按三档规则递减。
- 骨架 / 填空题里的提示注释不算正式注释，用户填完后要回头检查哪些提示该删。
